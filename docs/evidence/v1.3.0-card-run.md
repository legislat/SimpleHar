# v1.3.0 card evidence - CPU llama RAM booking

Freed-window run 2026-11-05 against the commit that became v1.3.0 (`9e7ddb7`,
the W2 step 3 build). The harness ran on the standard test ports, with no
control token, on a 72 GiB card and a 95.1 GiB host. The operator's model
serve was stopped for the window and restored after it; no other process
served the card. Test rows were CPU-only llama rows over the small and mid
GGUF files (0.6 GiB and 10.0 GiB on disk).

## Phase 1 - eviction under RAM pressure

The RAM reserve was raised to 60.8 GiB to create the shortfall on purpose.

| Step | Result |
|---|---|
| Card before any load | 3791 MiB used |
| Load the 0.6 GiB CPU row (RP) | 1.7 s; VRAM `need_gib` 0.0, RAM gate figure 2.5955 GiB |
| Card after the row | 4148 MiB (+357 MiB, llama CUDA context) |
| Load the 10 GiB CPU row (WORK) | path **Drain**, gate target 12.002 GiB, free at admit 10.331 GiB, victims `[test-cpu-rp]`, release 2222 ms, spawn 2273 ms, install 7273 ms |
| Victim outcome | `evicted` after the confirmed release (EVID-01) |
| Card after both | 4268 MiB (second CUDA context, no model bytes) |
| VRAM ledger | `booked_gb` 0.0 throughout |

The harness log named the decision, the deficit (1.67 GiB), the closed engine
port (18110), and the terminalized victim row.

## Phase 2 - serve and measured booking

The reserve returned to the default 8 GiB.

| Step | Result |
|---|---|
| 0.6 GiB CPU row | served chat completions at about 60 tokens/s |
| Measured pair, small row | re-booked from 2.5955 GiB to 1.4154 GiB; the row gained `measured_ram_gb: 1.4`, `measured_ram_gb_min: 1.4`, `measured_offload: true` |
| 10 GiB CPU row with a declared 2 GiB floor | served chat completions; the harness stayed up past 60 s |
| Measured pair, mid row | `measured_ram_gb: 9.4` - max truth over the declared floor |
| Unload | `unloading`, then `releasing`, then empty; release confirmed in the log |

## Reading

- A real CPU llama load serves: yes.
- Booking comes from host RAM, never `vram_gb`: yes (`need_gib` and
  `booked_gb` stay 0.0 on the card).
- Eviction under RAM pressure with a confirmed release and a settle before
  spawn: yes.
- No GPU job was evicted and no foreign process was touched: yes (only the CPU
  RP row was a candidate).
- "Zero card movement while it serves" is accurate for bookings and model
  bytes. Each llama-server process still creates a CUDA context of about
  0.35 GiB. This is llama.cpp behaviour for any llama row, not a harness
  booking. A pure-CPU llama build would be needed for a literal zero.

One harness instance terminated without a shutdown line during an earlier
phase while the operator used the same page; it did not reproduce in a 60 s+
rerun and left no crash record. It is recorded here so a repeat is
investigated.
