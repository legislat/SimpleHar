# v1.3.2 card evidence - Maya engine and host-RAM reclaim

Freed-window run 2026-11-06 against the Project Maya engine (commit
`2de4725`, decision `82bb48f`). The machine had one 72 GiB-class card and
95.1 GiB of host RAM. The operator's Basalt serve was stopped for the
window and restored after it; no other process served the card. Zero
subagents were active during the window.

## Setup

- The harness ran on loopback with the dedicated test ports 8790-8793 and
  the repo model rows. The catalog reported 28 rows and zero scan errors.
- Two rows carried the run: `maya-m` on the WORK slot and `maya-l-glp` on
  the RP slot. Both published `cost: greedy`, a 60 GiB launch floor, and a
  `load_timeout_s` of 1800.

## Refusal with the foreign resident

The window started with the operator's serve on the card. The harness
refused the first load and left the slot empty:

| Step | Result |
|---|---|
| Load `maya-m` before the serve stopped | HTTP 503, reason `below_launch_floor` |
| Floor figures | 60.0 GiB required, free 0.3 GiB, reserve 2.0 GiB |
| Unreleasable memory | 69.4 GiB held by the foreign resident; no release meets the VRAM floor |
| Slot outcome | the WORK slot stayed `empty` |

The operator then stopped the serve, and the harness re-admitted against
the measured free memory.

## Host-RAM reclaim for expert-offload engines

A second phase in the same window exercised the 1.3.2 reclaim rule. Two
CPU-only llama rows served on the AUX slots: a 7.6 GiB row booked at
8.0 GiB and a small row booked at 2.5955 GiB. With the foreign serve still
on the card, the `maya-m` load was refused at the launch floor and both CPU
rows stayed serving: the reclaim gate runs only after a successful VRAM
admit.

The serve was then stopped. The card fell to 3,513 MiB, and the harness
admitted `maya-m` through the `Drain` path:

| Field | Value |
|---|---|
| Free at admit | 65.4168 GiB |
| Gate target | 60.0 GiB |
| Victims released | `card-cpu-large` |
| Release | 4,444 ms, then the RAM settle, then one spawn |
| Install to serving | 62,248 ms |
| Reclaimed | 8.0 GiB |
| Threshold | 4.0 GiB |
| Skipped | none |

The event line names the model, the threshold, the evicted row, the
reclaimed 8.0 GiB, and an empty skip list. The small row (2.5955 GiB, at or
below the threshold) kept serving through the Maya load and unload. The
Maya slot served `glm-5.3-flash` with 131072 context and answered a chat
(16.3 tok/s); its unload released the card in 4 s (VRAM 71,475 -> 2,455
MiB). The model catalog reported `context: 131072` for `maya-m` from the
scan carry.

## Reading

What this run proves:

- The harness launches the Maya engine and reaches `serving` on both slots.
- The staged config strips the harness-owned keys and forces model
  management off.
- The readiness door (`/health`) reports the served id, the context limit,
  and the absence of an API key.
- The model-management doors stay closed: unload and direct chat on the
  engine port answer 404.
- The swap runs serially through the scheduler: each unload releases the
  card before the next load is admitted.
- A greedy expert-offload admit reclaims CPU residents above the 4.0 GiB
  threshold after the VRAM gate, before the spawn; a row at or below the
  threshold stays.
- Unload frees the VRAM and closes the engine port within seconds.

Honest limits:

- Host-RAM booking for GPU rows is still not modelled. The 1.3.2 rule
  reclaims large CPU residents; it does not book the expert tier.
- Maya's dashboard doors (`/api/port`, `/api/context`, `/api/update`) stay
  on the loopback slot. Do not use them on a managed instance.
- The 10 s load on Maya-L-GLP is a warm number: the model pack was cached.
  A cold load needs the 1800 s load timeout.
- The owed card legs (stalled-volume `first_bind`, strata `--port`, B8
  prefetch timing, 50-run log collision, pinned-exe last-wins) were not run
  in this window and remain open in the task record.
